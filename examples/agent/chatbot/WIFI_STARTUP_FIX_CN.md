# 已保存 Wi-Fi 的启动连接修复

现象：设备重启后使用缓存 Wi-Fi 连接不成功，再重启一次可能成功。

代码检查发现，原 demo 在启动 STA 后收到任意 `Disconnected` 事件就立即启动 SoftAP 配网。
Wi-Fi 服务本身会在意外断开后重试，而 `TriggerSoftApProvisionStart` 会禁用自动连接并触发 STA 断开。
两条流程会互相干扰。因此首次短暂失败就可能让设备退出自动重连，进入配网模式。
这是已确认的代码路径冲突，但没有现场日志，不能断言它是该设备现象的唯一原因。

本次修改：

- 有保存记录时启动 STA，并留出 60 秒连接窗口；期间断开仅记录日志，交给 Wi-Fi 服务重试。
- 到期查询当前状态。已连接则结束启动流程；仍在启动/连接中则每 5 秒复查；
  只有处于 `Started`（STA 已启动但没有连接进行中）时才回退配网。
- 查询失败不会直接当作连接失败；手动停止 Wi-Fi 后不强制开启配网。
- 连接成功会使旧回退检查失效。启动、事件清理和回退任务使用同一个串行调度组。
- 无保存记录时仍立即进入配网；不删除、更改缓存密码，不通过自动重启掩盖故障。
- 启动入口增加初始化/调度失败日志。

主要入口为 `main/modules/wifi_provisioning.cpp`，状态判断在 `wifi_startup_policy.hpp`。
此修复不解决底层驱动永远停在 Connecting 的问题；这种情况下检查会继续等待，须通过串口日志定位。

验证：主机测试覆盖仍在连接、已连接、重试停止、查询失败及主动停机的决策；
配网模块使用真实项目头文件及 SDK 替身通过 C++23 语法检查。没有完成 ESP-IDF 全量构建或实机验证。

实机复测建议保持原有 Wi-Fi 保存记录，连续测试冷启动和软件重启。若仍失败，记录从上电到首次失败后
至少 60 秒的串口输出，重点保留 `WifiProvisioning`、Wi-Fi 断开原因、重试日志、获取 IP 事件和内存错误。
分享日志前遮盖 SSID、密码及 token；不需要先清除 NVS 或重新配网。
